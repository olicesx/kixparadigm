# 长任务上下文管控：甜点阈值与自动适配

2026-09-12。回答两个问题：**长任务里压缩应该在多大上下文触发**，以及**新模型加进来要不要手工配**。
结论与证据都在这里，工具在 [`scripts/context-budget/`](../scripts/context-budget/)。

---

## 1. 结论

```
T = min(maxThresholdTokens 200K, 0.8 × W)     压缩触发阈值
R = min(maxRetainTokens   64K, 0.044 × W)     压缩后逐字保留的尾部预算
不变量：R ≤ 0.4 × (T − F)，F ≈ 23K
```

1M 窗口路由实测落地值：**T = 200,000 / R = 44,000 / 可压头部 133,000**。

`maxThresholdTokens` / `maxRetainTokens` 需要 `scripts/context-budget/kix-compaction-cap-patch.mjs`
给引擎补上——上游 schema 只有比例（`assertRatio` 限定 (0,1]），表达不了"任何窗口都不超过 N"。

## 2. 为什么是 200K：三条独立约束的交点

| 约束 | 证据 | 指向 |
|---|---|---|
| 成本随上限单调上升，能力在测量区间内持平 | 本机 11 条臂，见 §3 | 取下限 |
| 可压头部不能被子预算吃穿 | 事故根因，见 §4 | **T ≥ 183K**（R=64K 时） |
| 有效上下文利用率 10–20%；市面多针检索可用 ~200K | BABILong 类结论 + 2026 MRCR 横评 | **T ≤ 200K** |

上界与下界夹出的区间是 183K–200K，200K 是其中唯一可用圆整点。这不是折中，是三条独立证据同时夹出来的。

## 3. 实测：成本与能力

同负载（deepseek-flash，22 个 ~43KB 文件，逐文件读取并写参数到文件），**同为 27 请求**：

| 压缩上限 | 累计 prompt token | 相对 200K | 召回 | 压缩错误 |
|---|---|---|---|---|
| **200K** | **2,631,423 / 2,804,494**（两次采样） | — | PASS | 0 |
| 256K | 3,570,889 | +31% | PASS | 0 |
| 400K | 4,683,844 | +72% | PASS | 0 |

成本近似**正比于上限**（峰值 266K/197K ≈ 3.57M/2.72M）。三个档位的能力**完全无差异**：
召回全 PASS、压缩保真全 PASS、标定（8-needle + 序数检索）在 20K–400K 实测 prompt token
全对且未测到拐点。所以 256K/400K 买到的是"更多逐字工作区"这份保险，而本轮没有任何一条臂
证明这份保险被用到。

**上限是决策阈值，不是硬墙**：实测峰值可超出名义值一个步长的增量（D1 峰值 265,728 > 262,144）。

**批处理比上限更主导成本**：同一 400K 上限，压缩器关掉时 11 个请求就完成（更便宜），
而逐文件读取要 27 个请求。跨臂比较成本必须控制请求数，否则会得出相反结论。

## 4. 事故根因（为什么要加不变量）

`session-c3370a1e`：46 次压缩启动 / 36 次产出摘要 / 10 次因"选段太小"失败，累计 prompt
131,049,620，峰值 449,513。原因不是阈值太高，而是**可压头部被吃穿**：

```
旧配置：T = 0.18 × 1M = 180K，R = 0.16 × 1M = 160K，F ≈ 23K
可压头部 = 180K − 160K = 20K，扣掉固定前缀后实际只剩 ~1.8K
```

于是每轮压缩只能腾出 1.8K，21 步里触发 41 次，**每次对 prompt 的中位变化 +50 token**——等于没压。
由此得到不变量 **R ≤ 0.4(T − F)**：保留预算不得超过可压头部的 40%。

## 5. 未知模型：能不能自动适配

未枚举的 `(provider, model)` **不会崩**：回退顶层策略，按该模型上报的 `contextWindow`
现算 T/R，且**每个请求重新解析** → 会话中途换模型也自动跟随。但比例编码有两个盲区
（`kix-adaptation-sweep.mjs` 对完全未枚举的路由扫描得出）：

| 窗口 | 比例编码（0.2 / 0.044） | 绝对上限（`T = min(200K, 0.8W)`） |
|---|---|---|
| 32K | T=6,553，头部 **−17,888**（不可用） | 头部 1,773（仍不可用，F 占 70%） |
| 64K | 头部 −12,776 | 头部 26K ✓ |
| 128K | 头部 **−2,553**（压缩静默失效） | T=104,857，头部 76K ✓ |
| 256K | 头部 17,894（窄但可用） | T=199,999，头部 165K ✓ |
| 1M | T=200,000 ✓ | 同 ✓ |
| 1.25M / 2M / 4M | 250K / 400K / 800K（**无上限**） | 全部 200K ✓ |

**第三个盲区是 W 本身**：新模型若没在 settings 目录声明 `contextWindow`，会退回适配器默认值
（deepseek 1e6、pi-ai 262144）。一个真实的 128K 模型会被当成 1M，于是 T=200K 超过它真实窗口，
只剩 provider 溢出兜底。

所以：**加新模型必须做两件事——① 目录里写对 `contextWindow`；② 窗口 <200K 或 >1.25M 时补一条
`modelPolicy`**（1M 附近的大模型什么都不用做）。换成绝对上限后，第 ② 条不再需要，
`modelPolicies` 可以清空；<64K 窗口是物理限制（固定前缀就占 70%），配置层解决不了。

## 6. 为什么不开 kix-budget

| | 常驻预算（kix-budget） | 甜点阈值 |
|---|---|---|
| 累计 prompt | 875,750（5.3× 便宜） | 2.6–2.8M |
| 机制 | 每个 >2KB 结果**到达即**剪成 1.5KB | 到阈值才剪，保留完整工具结果 |
| 内容密集任务 | 需读两遍才对（12 次 vs 6 次） | 6 次 |

且它的 `resultThresholdChars` 调不动（`prunerThreshold()` 优先取宿主 pruner 的
`thresholdChars`），400K 交接 gate 在所有臂里从未触发（**未验证**）。要降成本，降上限比开它干净。

## 7. 运维

```bash
# 落地（备份→写入→校验→重启→失败回滚）
scripts/context-budget/kix-apply-abs-cap.sh            # dry run
scripts/context-budget/kix-apply-abs-cap.sh --self-test
scripts/context-budget/kix-apply-abs-cap.sh --restart
```

**配置与重启必须同时发生**：未打补丁的进程遇到未知键会中止挂载。因此
`--restart` 用 systemd 瞬态单元延迟执行：先等发起会话静默，再改配置、校验、重启。

**补丁会被 dsh 升级覆盖**（node_modules 被替换）。drop-in
`/etc/systemd/system/dsh-web.service.d/kix-cap-patch.conf` 在每次启动跑一次 `--apply`，
前置 `-` 保证打补丁失败也不阻塞启动：

```ini
[Service]
ExecStartPre=-/usr/local/bin/node /root/kix-compaction-cap-patch.mjs --apply
```

**回滚**：`agent.cordis.yml.bak-abscap-<stamp>` + `systemctl restart dsh-web`。

**诊断**：`kix-context-audit.py` 从会话日志重放预算信号——连续释放量过小、累计重读量、
压缩失败次数、以及"压力越过隐含阈值但裁剪与压缩都没发生"这个**静默失效签名**
（`--ratio` 指定当时的阈值比例）。

## 8. 证据边界（残余不确定性）

- 甜点值由"读文件 + 写参数"的合成负载夹出；**没有测过任何需要 >200K 逐字上下文的真实任务**。
  若出现这类任务，回 256K 是一行改动。
- 标定只覆盖 deepseek-flash 与 glm-5.3；其它路由按各自窗口代入同一公式，未逐个标定。
- 定价 token 与 provider token 在密集合成语料上比值约 1.44–1.5×（保留预算按定价计量）。
- 各臂 1–2 个样本，属方向性证据而非分布证据。
