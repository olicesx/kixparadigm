# kix 通用范式推进方案：目标延续、证据有效性与整体结算

> 日期：2026-09-08。本文保留研究阶段的方案与当时证据。后续已实施机械故障修复、最小认知改写及安装同步，实际范围与运行态验收见 [kix-runtime-verification.md](kix-runtime-verification.md)；下文“本轮未实施”等措辞指研究阶段，不代表当前安装状态。候选认知文本和提醒的通用净收益仍未完成对照验证，也未发布新版本。
>
> 适用范围：新功能、修 bug、重构、性能优化、依赖与数据迁移、PR 审查、跨轮继续及多代理交接。PR3194 是事故线索，不是所有任务的判定模板。

## 1. 推进判断

推荐保留 kix 的自编排、最小认知层、证据优先与规则退役原则，补强它们在多轮任务中的连续性。

需要贯穿任务的对象是**用户目标、适用约束、当前方案、当前材料以及证据的适用范围**。旧 finding 清单、旧实现、测试通过次数、子代理完成数量都是局部信息，不能替代这些对象。

最小推进方向是：

1. 先修准机械事实：失败不能被记成成功，旧版本或无关执行不能充当当前结论的验证。
2. 将“写码前”的方案必要性判断延续到后续修补、复核、优化和交接；继承目标，允许推翻旧方案。
3. 让结论强度与证据覆盖相符；局部修复、行为正确、目标满足、可交付是不同主张。
4. 用跨任务正反例验证收益；新增规则、提醒或成员必须证明净收益，不能靠这份方案自证。

不建立固定的“规划→开发→QA→审查”团队序列，也不要求每轮全量重审、每个任务写表或新增一个全局判定器。

## 2. 先校正 PR3194 的研究结论

### 2.1 可以保留的观察

- 原复核草稿在旧主要 finding 的关闭状态和构建/测试结果后给出 APPROVE；同时把公共 dialer 改动放在非阻塞备注里，并保留端口语义未验证项。
- 三次探索运行都给了 APPROVE。第三次全量审阅报告为 0 blocking / 4 major / 6 minor，其中一条 major 指向核心代码与 CI，建议拆分和额外复核；总体结论仍是 APPROVE。
- 这提示“旧问题关闭”可能占据了过大的判断权重；也提示列出更多疑虑并不必然改变总体结论。
- 维护者批评后作者调整了修复，但不能凭回退行为判定每个被撤回改动在技术上都错误。回退后的 TOML 行处理还出现了已知边界问题。

### 2.2 撤回的推论

此前“范式占 70%、模型占 30%”“唯一变量是任务框架”“预注册第三行被严格命中”“判据在场即可修”等表述没有足够证据，应撤回。

原因：

1. 原预注册第三臂是 `subagent_cross + 补充判据`，实际在看到第一臂结果后改成了普通 `subagent + 全量审阅`，没有按原方案执行。
2. 任务指令、要求比较的基线以及关注范围一起改变，不能分离各自效果。
3. 实际 provider、模型版本、继承的 persona、完整工具面未核查；工具名不能证明裸模型或独立权重对照。
4. `prereg.md` 及已产生的 `results/` 位于各臂可读的共享目录。未审计访问轨迹，存在结果污染风险，但也不能直接断言子代理读过这些文件。
5. 每格仅一次；“建议拆 commit”与“拒绝当前方案”不是同一个终点。三次均 APPROVE，未证明决策层已经纠偏。
6. 保存的 arm1–arm3 文件是协调者摘要，不是完整原始输出或运行轨迹，不能当作完整复现实验包。

本事故属于**探索证据**。其价值是生成可证伪的假说，而非给模型和范式划责任百分比。

### 2.3 防止以错误方向修范式

- 公共包、CI、新依赖或跨文件修改，不自动等于越界。它们可能正是正确修复所需。
- 采用成熟 TOML 解析库，可能比继续修补手写扫描更符合 KISS；多一个依赖不自动增加总复杂度。
- DRY 要证明共同变化原因，相似文本不自动要求抽象。
- “未使用 `/kixpower-review`”不能单独证明因果路由失效；普通语言任务仍受常驻原则约束，也可以主动读取相关技能。需要实测的是决策时刻是否获得了适用信息。
- 现有冻结原则也没有限定只适用于自己编辑。应检查机械覆盖和信息传递，不能从表述缺少某个词断言原则完全缺席。
- 未验证项可以是非阻塞项；需要判断它是否影响当前交付承诺，不能统一升级或统一放行。

### 3.1 已重放的机械反例

独立观察者创建的外部临时探针 `/tmp/kix-discipline-green-probe.js` 调用真实插件 handler，模拟一次源码编辑，随后分别送入三种测试结果。本主线程读过脚本并重新执行，结果一致：

```text
A. bash pnpm test exitCode=1 (no isError): green-reminder=false
B. bash pnpm test {isError:true}:          green-reminder=true
C. bash pnpm test exitCode=0 (no isError): green-reminder=false
```

A 应与 B 一样不能清除未验证提醒，却与 C 同形。这是**真实插件＋合成宿主事件**的行为反例，尚不是安装后 GUI 的端到端回归，也不证明它导致了 PR3194 的具体结论。

需先固化为仓库测试，并补实际工具链集成验证。探针本身退出 0 只表示脚本运行结束，不表示测得行为正确——这也是本次推进要消除的混淆。

## 4. 通用失效模型

将根因保留为以下候选，而不把“范围外文件”固化为错误标签。

| 候选失效 | 通用编码中的表现 | 缺的判断 |
|---|---|---|
| 目标被局部清单替换 | 修完异常便声称功能完成；任务分解后只核对各子任务完成 | 最初用户结果和约束是否仍满足？ |
| 旧方案获得默认豁免 | 加重试让测试通过，却改变幂等语义；加缓存掩盖接口不一致 | 新方案是否值得、是否改变约定？ |
| 证据被扩大解释 | 编译通过⇒迁移安全；微基准快⇒生产延迟好；截图好看⇒交互可用 | 证据具体支持哪项主张？ |
| 证据与材料脱离 | 上轮独立观察、旧测试结果、另一 worktree 的检查清除了本轮疑虑 | 被验证的是哪个目标、版本和环境？ |
| 独立观察继承了答案 | 给 QA 一份“已修好这五处”的清单；丢掉原始目标和未决约束 | 观察者是否有机会推翻总体结论？ |
| 结论与正文不一致 | “全部完成”，正文却有会影响交付的关键未知；实验换臂后仍宣称预注册成功 | 当前证据是否真的足够支持这个动作？ |

这些候选在新功能、修 bug、优化和审查中可以同构出现；其发生率与干预收益尚需通用任务验证。

## 5. 认知层：用四项改写覆盖整个任务生命周期

以下是**候选文本**，供最小对照试验使用，不是已经验证的新增规则。实施时替换/合并现有需求三检、二相性、写码前及结算表述，不把四段原样再叠加一遍。

### 5.1 目标和约束延续，旧方案可推翻

> 后续继续、修补、复核与交接，沿用当前用户目标和仍适用的约束；用户改约就更新约束。旧方案、任务清单和旧 finding 只是线索，不替代验收。关键约束缺失时恢复其来源，不把自己的偏好补成用户要求。

这对普通任务在当前上下文内即可完成。跨轮、跨代理或确有丢失风险时，才把最小必要内容写进已有契约/交接文档。

来源顺序应尊重有效指令与用户授权：明确用户要求、适用项目契约与稳定接口语义，优先于经验偏好、类比和模型建议。维护者一句泛化批评不能代替具体契约。

### 5.2 每次实质变化都重新评价方案

> 方案引入新的行为、依赖、公共接口或维护负担时，对照原目标与真实约束重新判断必要性和净收益。正确修复允许扩大实现范围；最小化比较总复杂度与风险，不比较行数。已授权范围内可自主推进，不把普通技术选择变成反复请示。

重试、缓存、fallback、schema、默认配置、构建依赖都可能是实质变化。反之，触及十个文件也可能只是必要的机械迁移。

“本 PR 是否应承担此改动”作为方案与范围适配的一项判断，复用架构/契约判断即可；不新增人人必填的第八维，也不借用 ownership 一词混淆资源所有权、用户授权和代码维护职责。

### 5.3 证据只在适用条件内有效

> 证据依附于被验证的主张、材料、约束和环境。材料或依据改变，只重开受影响的判断；无法判断影响时明确未知。测试通过、工具成功或代理完成都不能单独推出整体完成。

更新行为接口后，相关调用方与测试的证据要重判；修改无关说明不要求重跑整个系统。环境变化可能只影响运行时验证，代码未变也不一定足以保留旧性能结论。

### 5.4 总体结论按当前目标结算

> 交付前用当前材料核对用户目标与方案约束，明确证据覆盖和会改变结论的未决项。旧问题修复是局部结果；宣称完成或可交付，需要足以支撑该承诺的证据。已知非阻塞限制可接受，但不能同时称其为必须解决又给无条件通过。

简单任务可以一句话结算，不强制输出四栏报告。重要结论若仍存在会改变实现或交付判断的语义缺口，选择能够补足它的独立观察或实证；人数不计分，多数不裁决。

## 6. 上下文与证据如何承载

### 6.1 最小任务状态，复用现有入口

逻辑上要保留：当前目标、适用约束及来源、当前材料/基线、已覆盖与未决主张。这不是要求新增数据库或每任务注册 schema。

- 单轮低风险任务：当前上下文足够，不新增文件。
- 多轮当前任务：复用 `kix_discipline_spec.contract`，把任务标识、来源、关键假设和变更理由写入已有文本字段，不先增加必填 API 字段。
- 多代理派发：传递一份任务对应的契约内容或明确引用，绑定使用时的版本；不能让多个并行任务都去读随时被覆盖的共享 spec.md。
- 跨会话继续：从已有 plan/progress/handoff 或明确任务引用恢复；共享 spec.md 仅是入口，必须核对属于哪个任务。用户已改约，旧快照只作历史证据。
- 只有确有并发覆盖需要时，使用现有任务产物目录中的任务专属快照；不为每次工具调用制造一份状态副本。

### 6.2 证据的最小关系

概念上记录如下关系即可；先复用现有 command/job/epoch/报告引用，只有缺口经验证后才增加机器字段：

```text
evidence → source(call/job/report) + subject/artifact + revision/context
         + scope/claim + observed outcome + limitations
```

这里分开四件事：结果是否收到、是否执行成功、与当前结论是否相关、是否足够支持结论。最后两项主要需要语义判断。

- failed、killed、timed-out、尚在运行、结果无法解析，不算成功。
- 源文件、依赖锁、测试夹具、生成配置与已声明契约都可能影响有效性；commit SHA 不含工作区脏改动，不能单独代表当前状态。
- 不能读取指纹或版本时标 unknown，不把 unknown 当干净；也不因 unknown 自动要求无限重跑或用户确认。
- 任意一次成功 `run_code` 只能证明程序成功返回。纯读取和结果汇总不应自动清除实现验证缺口。
- 真正执行测试的工具即使返回 0，也仍有覆盖边界。以同一库编码再解码可以是有用单测，但不能替代真实消费者兼容性的证据。

### 6.3 独立观察保留目标，隔离主张者论证

沿用现有成员和 read-only epoch，不新建角色。

- discovery 观察：给原始目标、适用契约、材料与入口；不先灌“这些都修好了”“方向肯定没问题”的摘要。是否需要该观察由实质缺口决定。
- claim verification：可以给要验证的确切主张、来源与反例入口；要求独立读事实，不把执行者给的理由当结论。
- 所有观察都保留必要的用户约束；“独立”不等于剥掉领域背景。旧 findings 可以作为上下文，但应标明不穷尽问题空间。
- 已在路上的同一 probe 不重复执行；遇到可改变实现的 design observer，先结算再编辑目标。
- 观察者完成只意味着报告可消费。父线程仍须解释其适用范围、有效反例与未覆盖部分。

不采纳“报告不含 disputed 关键词就算 clean”的修法：引用、否定、语言变化都会破坏它。若后续有明确结构化结果协议，机器可校验协议完整性，仍不能据此认证语义结论。

## 7. 机制层：按证据强弱分批改

### M1：修正执行成功谓词——已具备修复依据

首个实现包只修机械事实，不夹带新认知策略。

- 把 `kix-discipline` 对测试/lint 成功的判断与实际工具返回契约对齐。
- 对齐 `kix-settle` 已有的终态判断语义，避免两份谓词漂移。实现时注意 settle 已依赖 discipline，不可反向 require 引入循环；可在已有合适 helper 中复用，确有两个消费者再提取小公共函数。
- spawn/running 不能提前清账；后台成功要绑定启动时材料状态，相关修改后到达的旧 job 不能直接认证新版本。
- 未知工具返回形状不当成功，也不禁用合法工具；报告缺口并让模型选择验证路径。
- 复核测试与 lint 是否遵守执行先后：在测试成功之后再次修改相关实现，不能继续宣称最后修改已验证。

验收：非零、超时、取消、基础设施错误、sandbox 拒绝、运行中、过期 job、当前成功结果在测试中能区分；至少重放一个真实 bash 失败和一个后台终态链路。不能再用仅 `{isError:true}` 的 stub 代表所有失败。

### M2：明确证据与结论的关系——先记录/离线审计，再考虑提醒

- `freshObserverSeen` 不再被描述为当前主张已独立验证；会话级执行次数不代表所有结果都已验证。
- 复用调用 ID、子代理 lineage、job ID、当前 edit generation 和已声明 epoch 做事实记录；不做全仓语义依赖图。epoch 关联以分派声明为准，可复用已导出的 `extractReviewEpochMeta`；活跃 epoch 注册表是 orchestration 的闭包私有状态，不新增跨插件 epoch 服务或第二份权威注册表。
- 如需当前观察完成状态，至少关联本次对象/epoch；未声明关联时是 unknown，而不是把旧会话布尔值升级为有效。
- 先在离线审计报告“可能用了过期/无关证据”的候选，不直接发否定裁决。
- 只有 live trial 证明该候选提醒能纠偏且不频繁误扰，才合并入现有 `kix-settle` 的一次性 advisory；不并列堆积多个“再检查一次”。

验收：换任务、换 worktree、外部更新、旧观察返回、读取型 run_code 不会被报告为当前语义已验证；真正相关的测试/观察仍可复用。没有语义映射证据时，审计明确标“候选”。

### M3：契约与材料一起考虑——显式关联，不扫描所有隐含状态

- 复用 review epoch 起止检测，只加入本任务**明确依赖的契约快照/配置输入**，不能盲目把整个共享 `kix-discipline/` 纳入所有 epoch。
- ignored 的契约不能靠 Git 指纹自动覆盖；对明确引用的输入读取内容指纹。mtime/size 对同尺寸变更不够。
- 契约更新由用户或有效需求澄清产生；检测到变化表示旧结论需重判，不能把用户改约当成违规阻断。
- 观察结束后若对象继续变化，旧报告保留为历史证据，当前适用性由新材料比较决定；不维持无限期全工作区锁。
- 非 Git 目录、不可读输入、未声明任务关联均诚实标 unknown；不承诺全覆盖外部更新。

验收：契约相关变更可见，无关任务覆盖共享 spec 不误伤当前快照；代码没变但验收条件改变会重判；无关文案不触发无意义全量验证。

## 8. 输出语义：事实、判断、动作分开

复用现有机制/契约/影响三层，不把原则口号当缺陷证据，也不继续用单个彩色标签承担全部含义。

| 表述 | 支持范围 | 不可外推为 |
|---|---|---|
| 测试运行成功 | 指定环境与测试覆盖的行为 | 所有平台、真实部署、架构合理性 |
| 旧缺陷已关闭 | 那条缺陷的触发条件与修复证据 | 当前改动没有新问题 |
| 材料变化 | 被声明观察的对象有差异 | 变化必然危险或必须重跑全部测试 |
| 方案不符合明确契约 | 有来源的约束与违反事实 | 原则名本身就是 bug |
| 某维护者不愿合入 | 可追溯的项目处置决定 | 每个被拒改动都技术错误 |
| 可交付 | 当前目标、约束与关键风险有足够证据 | 没有任何不确定性 |

建议将“影响严重度”“证据状态”“当前处置”分开表达，仅在有必要时列出：例如“命名偏好，非阻塞”；“兼容性关键主张未验证，当前不能声明迁移完成”；“违反明确依赖政策，需调整方案”。不能因为是架构意见就默认轻，也不能因为维护者不喜欢就判安全 blocking。

`只报 bug 不给方案` 保留其防止把未经验证建议当指令的意图，改为有任务边界的表达纪律：审查默认给证据和影响；用户要求方案时应给出有边界的方案；编码任务当然要实现方案。不要用“建议/应当”等词的正则去拦截输出。

## 9. 跨任务应用与反例

以下是候选评估场景，不是已发生事故，也不是要求 agent 每项逐条检查。

| 任务 | 正向检测场景 | 必须允许的反例 |
|---|---|---|
| 修 bug | 加重试让测试绿，却造成重复收费/写入 | 经过幂等设计与真实失败用例验证的必要重试 |
| 新功能 | 局部 endpoint 可用，但漏掉原定权限或跨租户隔离 | 为满足权限契约必须修改共享鉴权层 |
| 重构 | 文件更少，却改变动态分派/生命周期 | 正确抽取有共同变化原因的公共 helper |
| 性能优化 | 微基准加速，真实 workload 内存或尾延迟变差 | 有代表性基准支持的较大架构调整 |
| 依赖/数据迁移 | build 绿，但部署目标不支持或数据不可逆损坏 | 引入成熟解析/迁移依赖，比自写方案更稳健 |
| UI/跨轮迭代 | 截图达标，键盘焦点或原交互目标丢失 | 用户明确改变目标后，不应继续坚持旧设计 |
| PR 复核 | 只核对旧 finding，没有核对新增行为及当前整体结论 | 问题完全修复且新增 CI 正好覆盖新增能力，应可放行 |
| 交接/长会话 | 新代理读取了别的任务覆盖的 spec，执行错目标 | 已有足够上下文的短任务，无需再写快照/重复请示 |

有效改进应同时减少漏判、误拦和不必要工作；拒绝更多 PR、修改更少文件、写更多测试或派更多代理都不是收益指标。

## 10. 改进实验：测任务结果，不测口号出现率

### 10.1 先固定问题和终点

优先验证两条候选：

- H1：保持原目标/约束并限制结论外推，能减少多轮任务中的错误完成声明。
- H2：把动作发生与证据有效性区分，能减少过期/无关结果被用来支撑完成。

单独验证 M1 的返回值缺陷不需要模型实验；它是确定性的程序语义问题。不要把它的修复收益算给认知 prompt。

主终点是**对当前交付动作的正确判断与正确最终产物**，不是是否提到 KISS/范围、是否列出 major、是否拒绝更多任务。审查用冻结契约与独立核验的反例判定；编码用隐藏验收、真实消费者行为和最终 diff 判定。

### 10.2 最小比较，避免一次改完所有变量

1. 先用两个小 smoke case 验证材料隔离、采样记录和评分流程；这不是有效性样本。
2. 选择 6 个任务领域，每域一组“容易偏离”和“必要扩大实现/应当通过”的配对任务，共 12 个任务。PR3194 最多占其中一个，另保留未参与调提示的任务作为独立复验集。
3. 首轮比较同一实际模型下的当前默认配置与**只改认知锚点的配置**。任务原话、证据可见性、历史长度、工具面、环境、预算和温度保持一致。
4. 每任务每配置 3 次独立运行，12×2×3＝72 次。此数字只是本候选实验的计划规模，不是范式运行配额，也不宣称有统计功效保证。成本不可接受时，在解盲前缩小研究目标并重新注册，不能看结果后挑样本。
5. H2 如需模型级实验，另做独立干预对照；不要同时更换模型、角色、baseline 视图和证据提示。跨厂商复验也单列，不用工具名假定已控制模型。
6. 不能从这个实验推出责任百分比或所有模型的普遍规律。小样本报告每例胜/负/持平及成本，效应不稳定时不升格。

### 10.3 实验完整性

- 每次运行独立目录，只含允许材料；预注册、标签、其他运行结果与评分规则存于 agent 不可读位置。共享缓存只允许固定内容、只读使用；会话输出不混入刺激。
- 记录实际 provider/model、路由降级、persona/skill 内容指纹、工具集合、fixture/diff 指纹及命令环境。宿主公共规则属于基线的一部分，不把 fresh 宣称为裸模型。
- 保存原始输出、工具轨迹、最终材料和 terminal 结果；摘要只是索引。离线检查越界读取与共享写入，污染样本作废并记录原因。
- 评分者看不到实验臂；反例与可接受解集合在解盲前固定，允许没有采用参考修法但满足契约的实现。
- 维护者合入/回退行为仅作标签线索，需要具体理由、源码和真实行为支撑；“被合入”不自动是正确，“被回退”不自动是错误。
- 预注册变化记作新版本/探索分析；保留旧记录，不再宣称严格命中旧规则。

### 10.4 指标与升格

分别统计，不合成一个能掩盖回归的总分：

- **错误完成/放行**：材料违反有效契约或关键主张未有证据，仍声称目标完成。
- **误拦/多余修改**：必要的跨包改动、依赖或正确方案，被无契约理由拒绝或改坏。
- **目标与约束保留**：交接/压缩/继续后是否仍满足原定结果，用户改约后是否正确更新。
- **证据一致性**：当前引用是否对应当前材料、环境和主张；没有把未执行说成已执行。
- **成本**：工具/模型调用、输入输出 token、墙钟、无效测试、重复观察和用户额外确认。

升格要求：在独立复验中，至少两个非 PR 领域重复出现经核验的净收益；没有新增关键安全/行为契约回归；误拦与用户中断未出现实质恶化；成本增加能由减少的错误解释。实际可接受成本/误拦界限在执行前由维护者按目标确定，不事后调阈值。

若收益只来自更长报告、更多拒绝或看到标签，失败。若连续两轮匹配任务无决策收益且增加成本，删/缩候选。无收益但零成本的文案也不能自动升格为原则。

## 11. 分阶段推进与依赖

这是工程推进顺序，不是每个 agent 任务都要执行的流程。

| 阶段 | 工作包与输出 | 放行依据 | 失败/回收 |
|---|---|---|---|
| P0 证据还债 | 本文纠正 PR3194 归因；保留原预注册；把 M1 反例转成回归用例并修成功谓词 | 真实结果形状、后台终态与失败路径区分，现有行为不过度阻断 | 修复未覆盖真实链路则继续取证，不升级为策略改进 |
| P1 最小认知候选 | 替换现有 3–4 处锚点，清理 skill/活跃 persona 的冲突；在开发副本试验 | diff 可读、承载明确、预算守护通过；不加固定角色或任务流程 | 出现整单全量重审/反复问权限，改写或退役 |
| P2 通用效果验证 | 按第 10 节做冻结对照，输出原始物证与盲评结果 | 跨领域复验支持净收益，反例未恶化 | 结论不确定就保留 candidate，不发布成功叙事 |
| P3 证据关联候选 | 根据 trace 缺口实施 M2/M3；先离线记录，再小范围 advisory | 旧证据/无关证据反例可复现，必要证据可复用；无提醒风暴 | 提醒无独有价值则回退，只留有用的事实记录 |
| P4 分发与真实任务 | 在开发/试验 preset 验证后同步目标变体和安装副本；用后续真实任务复核 | 默认自然语言路径有效；子代理继承正确；安装后新会话行为一致 | 回滚本轮候选配置，保留正确机械事实修复与失败记录 |
| P5 回收 | 把有效案例保留为短记忆，清理被新载体取代的重复承诺 | 后续匹配任务仍有净收益 | 两轮无实证收益删/缩机制，避免常驻税持续增长 |

P0 的确定性修复可以独立交付；P1/P2 不应等待复杂证据基础设施。P3 只在具体缺口及干预价值成立后做，不能为未来所有可能问题提前造状态平台。

## 13. 参考与证据边界

本次使用了主线程源码读取、独立设计观察、独立方法论审计和插件行为探针重放。独立报告中的建议并非全部采纳：不采纳 disputed 关键词判 clean、不采纳“所有契约文件自动进冻结”、不采纳以维护者合入/回退作为唯一真值，也不采纳把观察者完成计数改成投票机制。

外部资料提供方法参考，不是强制流程来源：

- [Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)（2026-01-09，已读取正文）：区分 task/trial/trace/outcome；模型与 harness 一起被评估；编码可使用执行结果，开放质量判断需校准的评分；能力评估与回归评估需要分开。这支持本方案区分“报告说完成”与“最终状态满足任务”。
- [Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（2025-09-29，已读取正文）：最小高信号上下文、按需检索、明确而不过度规定动作的指令。它支持保留目标和依据的短引用，不支持每轮加载完整流程。
- 本仓 [orchestration-lessons](../dsh/preset/memories/orchestration-lessons.md) 的“信息工具而非决策代理”“防 resulting”“自省归因须回原始证据”等教训，要求本次推进也接受反例。

临时历史证据索引：`/tmp/review2.md`、`/tmp/exp/prereg.md`、`/tmp/exp/results/`。它们不是长期实验档案；后续要复验时须先恢复并冻结原始材料，不能仅用协调者摘要。

当前仍未验证：候选认知文本的通用收益、M2/M3 提醒净收益、实际历史模型路由与隔离、安装后 M1 的完整事件链。本方案失败的一个明确情形是：加入目标/证据关联后，只让 agent 更保守、更啰嗦或更多请示，却没有减少真实错误交付；此时应退役候选，而不是继续增加规则。
